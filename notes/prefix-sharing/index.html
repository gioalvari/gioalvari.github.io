My benchmark found four bugs in my inference server

September 2026, updated with sticky memory and continuous batching · RadixForge, llama.cpp, local LLM serving

When eight agents share the same long system prompt, a local inference server should compute that prompt once. RadixForge, a small C++ server I built on llama.cpp, does exactly that. The first time I benchmarked it properly, it looked 130× faster than llama-server. It was not: it was broken. This is how the benchmark caught that, and what the real numbers are.

The idea

RadixForge keeps a radix tree of token sequences on the CPU. Each node points to llama.cpp sequence slots that already hold the KV cache for that prefix. A new request walks the tree, finds the longest cached prefix, attaches it to a fresh sequence with llama_memory_seq_cp, and only prefills the remaining tokens. It is the same idea as SGLang's RadixAttention, in about 2,400 lines of C++ on top of the public llama.cpp API, running on Apple Silicon with Metal.

llama-server already has a prompt cache, so the question is where a shared tree actually helps. llama-server's cache is per slot: a request reuses what its slot computed before. When many agents arrive at the same time and land on different slots, each slot recomputes the shared prompt.

The benchmark

I added a prefix-sharing experiment to local-llm-bench, my harness for reproducible local-inference measurements. It is server-agnostic: any OpenAI-compatible command line is a target. The workload:

  • 8 agents, each with the same ~1,500-token system prompt plus a short per-agent suffix;
  • 4 turns per agent, where later turns carry the real previous answers;
  • concurrency 1 and 8, 32 output tokens, temperature 0;
  • 3 repetitions, each on a freshly started server with an empty cache;
  • time to first token (TTFT) split by phase: the first request, the other agents' first turn ("fan-out"), and follow-up turns.

Model: Qwen2.5-0.5B-Instruct Q4_K_M on an M4 Pro. Small on purpose, so that runs are fast and the orchestration overhead is visible.

Four bugs, found by one table

1. The server never finished a streamed response. The very first run hung. The log had grown to 25 million lines in ten minutes. cpp-httplib calls a chunked content provider again and again until it calls sink.done(); mine returned without calling it, so every call re-enqueued the same, already moved-from request. Each empty request took a new sequence slot, and all 32 were gone within a second.

2. Slots leaked and could not be evicted. When slot allocation failed, the tree node's reference count had already been incremented and was never released. Eviction also only considered leaf nodes, but after a split the cached sequences stay on the parent, so the nodes that actually held memory could never be evicted.

3. The impossible result. With the first two fixed, the table showed RadixForge at 2 ms TTFT on follow-up turns: 134× faster than llama-server. The responses were empty. By default llama.cpp splits the context into one stream per sequence: 32,768 tokens across 32 sequences is 1,024 tokens each, and a 1,550-token prompt did not fit. The prefill failed, the error was streamed as content, and the harness measured a very fast failure. RadixForge now creates a unified KV cache: every sequence can use the whole context, and attaching a cached prefix only tags existing cells instead of copying them. The harness now counts empty completions and in-band errors as failures.

4. A race inside one batch. At concurrency 8, a third of requests failed. The worker prepared all queued requests before prefilling any of them, so agent B would reuse the prefix agent A had registered a moment earlier, but whose KV cache was still empty. llama.cpp rejected the batch because the sequence positions did not line up. Sequences are now pending until their prefill succeeds and are never used as a copy source before that. Requests that share a pending prefix are prefilled in a second round and then generate in the same batch.

None of these showed up in unit tests or in manual curl calls with short prompts. They all needed long shared prompts, concurrency and multi-turn history, which is exactly the workload the server exists for.

  • Concurrent fan-out is where the tree matters. With 8 agents arriving together, llama-server's cache reuses nothing (cache_n is 0) and is no faster than having no cache at all. RadixForge computes the prefix once: 288 ms instead of 1,857 ms, 6.4× lower.
  • Follow-up turns at concurrency 8 are a tie. Each agent's history lives in its own llama-server slot, which is the case a per-slot cache already handles well.
  • Generation is slower. RadixForge has no continuous batching yet. At concurrency 8 the median full response on follow-up turns takes 696 ms against 525 ms. Over the whole workload it still finishes in 2.98 s against 4.08 s (10.7 vs 7.8 requests/s), because the fan-out saving is larger.

Adding memory to the agents

I also maintain agent-memory-layer, a proxy that retrieves relevant past interactions with local embeddings and injects them into each request. My assumption was that injecting memories into the system prompt changes the prefix on every request and defeats the cache, so I added an option to put them at the start of the last user message instead, leaving the system prompt and history byte-identical.

Putting the proxy in front of RadixForge first exposed another bug, in the proxy this time: its embedding context was configured for one sequence while it packed up to eight into a batch. Under concurrency, retrieval silently returned nothing, and some requests hung for minutes. After the fix:

My assumption was only partly right. The proxy appends memories to the end of the system prompt, so the 1,500 shared tokens before them were cached either way. Moving the block saves the conversation history (22–25% fewer prefilled tokens on later turns, 28% lower TTFT at concurrency 8). The larger cost is the memory block itself: it changes on every request, so it is always recomputed. By the fourth turn a request prefills 231 tokens instead of 54. Making that block stable across turns is the next thing to work on.

Update: both open items

I have since worked on the two open items above. These runs used the same model and machine, but on battery power, so compare the columns with each other, not with the tables above. Each comparison ran in rotated order.

A memory block that stays cached. Clients resend the history without the blocks the proxy added in earlier turns, so the prompt changed at every turn. The proxy's new --inject-mode sticky remembers the block it added to each user message and puts it back byte for byte. It also skips memories already shown and writes absolute dates instead of "5m ago". Each prompt is now an exact extension of the previous one. By the fourth turn a request prefills 150 tokens, against 307 with the block in the last user turn and 362 with the block in the system prompt.

The new block still costs about 95 tokens per turn compared with no memory at all.

Continuous batching. RadixForge now runs one llama_decode per step. Each step carries the next token of every active sequence and the prompt tokens of any request that just arrived. New requests join the running batch, and finished or disconnected ones leave it at once. The synchronized 8-agent workload above does not change (2.96 s against 2.97 s). The difference shows when requests arrive while others are generating: 64 requests, one every 60 ms, three rounds.

The benchmark caught one more problem here. My first version was 6% slower on the synchronized workload, because the eight requests of a turn arrived a few milliseconds apart and each got its own prefill call. Putting prefill and decode in the same step, plus a 2 ms window to collect requests that arrive together, fixed it. The eight failures in the static column are the old server running out of sequence slots. Those requests now wait in the queue instead.

What I take from this

  • A benchmark for a cache has to check that the answer is real. A failure is always fast.
  • Measure against the strongest baseline configuration. llama-server with its cache is excellent for single-agent and per-agent reuse; the gap only exists for concurrent shared prefixes.
  • Report where you are slower. Here: tail latency of full responses, and every result on one small model on one machine.
